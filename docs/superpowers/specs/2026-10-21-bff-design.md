# BFF: сервер Hono + tRPC под целевой контракт Go

Дата: 21 октября 2026 года.

Задача: [frontend#2](https://github.com/Cringe-Driven-Development-Team/frontend/issues/2).
Ветка `web-2`, PR в `Cringe-Driven-Development-Team/frontend` с заголовком `WEB-2: BFF. Добавить`
и строкой `Closes #2`, ревью ментора.

Подробное «что сделать» и «приёмка» — в самой задаче, она остаётся главным списком требований.
Как устроены сессия, CSRF, роутер, HTML и образ, описано в треке BFF:
[контракт](https://docs.cellestial.ru/modules/2/tracks/bff/contract),
[сессия и CSRF](https://docs.cellestial.ru/modules/2/tracks/bff/auth),
[сервис](https://docs.cellestial.ru/modules/2/tracks/bff/service),
[серверный bootstrap](https://docs.cellestial.ru/modules/2/tracks/bff/bootstrap).
Эта спека не пересказывает их. В ней записано то, чего нет ни в задаче, ни в треке: решения
пользователя, решения исполнителя и порядок работы.

## Цель

В `apps/bff` появляется работающий BFF. Браузер получает от него HTML с текущим пользователем
и вызывает процедуры tRPC. BFF ходит в Go по Bearer и хранит токены в зашифрованной
HttpOnly-cookie, так что JavaScript браузера токенов не видит. Это основа для #46 (клиент tRPC),
#5 (перевод экранов) и #4 (CI/CD образа).

## Что уже есть

На `team/main` влиты #44 (монорепа) и #45 (Orval). В `apps/bff` есть только сгенерированный
клиент к Go (`src/go/client.ts`) и мутатор `bearerFetch` (`src/go/fetch.ts`). `@cdd/schemas`
содержит zod-схемы из `spec/openapi.json`. Hono, tRPC, `index.ts`, сборки и Dockerfile нет.

`spec/openapi.json` пока описывает **старый** Go: login/register отвечают `User`, токены приходят
в `Set-Cookie`, есть `X-CSRF-Token` и cookie `refresh_token`. Целевой контракт делает
[backend#41](https://github.com/Cringe-Driven-Development-Team/backend/issues/41), задача открыта.

## Решения пользователя

1. **Работа идёт в командном репозитории.** Фронт перенесён: ветка `web-2` от `team/main`,
   PR в `Cringe-Driven-Development-Team/frontend`, `Closes #2`.
2. **BFF пишется под целевой контракт Go**, а не под нынешний Go с cookie и не в ожидании
   backend#41.
3. **`spec/openapi.json` правится вручную** под целевой контракт. Это осознанное исключение из
   правила `AGENTS.md` «спеку руками не править»: в Apidog целевого контракта пока нет. В описании
   PR это отмечается. Когда backend#41 обновит Apidog, `bun run sync` заменит ручную правку
   выгрузкой.
4. **Приёмка — через `curl`, без браузера.** Браузерное поведение имитируется заголовками:
   «наш клиент» — `X-CSRF: 1`, свой `Origin`, `Sec-Fetch-Site: same-origin`; «чужой сайт» — чужой
   `Origin` или `Sec-Fetch-Site: cross-site`, запрос без `X-CSRF`, form-тело, а также `OPTIONS`
   без разрешающих CORS-заголовков в ответе; «внешняя ссылка» — GET HTML с
   `Sec-Fetch-Site: cross-site` и cookie. Cookie хранится в общем cookie-jar `curl`, две вкладки —
   два параллельных запроса с одной старой cookie. Раздача ассетов, страница чужого origin и
   браузерный клиент tRPC в объём не входят. Что браузер реально не отправит запрос после
   отказа preflight, проверит #46 на настоящем клиенте.

## Цели, не-цели, анти-цели

Цели — пункты «Что сделать» задачи; приёмка — её «Приёмка».

Не входит (как в задаче): клиент tRPC (#46), перевод экранов и чтение bootstrap клиентом (#5),
CI/CD (#4), изменения Go, production Caddy/Ansible/Compose, своя реализация tRPC/Zod, SSR,
`views.notebook`. Сверх задачи сюда не входит и dev-режим «Vite за BFF» из раздела
[«Разработка»](https://docs.cellestial.ru/modules/2/tracks/bff/bootstrap#разработка):
до #5 клиент ходит в `/api/v1` напрямую, и связка ему не нужна.

Анти-цели — при них задача провалена, даже если всё запускается:

- токен, срок токена или `SESSION_KEY` виден браузерному JS, попадает в bootstrap, ответ процедуры
  или лог;
- параллельные ответы разных пользователей смешивают данные;
- сломан действующий клиент: `apps/client` до #5 работает со старым Go через `/api/v1`. Правка
  спеки не должна изменить его код и сгенерированную схему;
- ручная спека расходится с тем, что опишет backend#41. Правка — ровно по списку из
  [«Что меняется в контракте Go»](https://docs.cellestial.ru/modules/2/tracks/bff/contract#что-меняется-в-контракте-go),
  без собственных изобретений.

## Правка контракта Go

Только то, что перечислено в треке:

- схема `TokenPair`: `access_token`, `access_expires_in`, `refresh_token`, `refresh_expires_in`
  (сроки — целые секунды), все поля обязательны;
- `POST /auth/register` → `201 { user: User, tokens: TokenPair }`; `POST /auth/login` → `200` того же
  вида;
- `POST /auth/refresh`: тело `{ refresh_token }` → `200 TokenPair`;
- `POST /auth/logout`: тело `{ refresh_token }`, `bearerAuth` → `204`;
- у всех операций убрать заголовки `Set-Cookie`, параметр cookie `refresh_token` и заголовок
  `X-CSRF-Token`; у ручек данных остаётся `bearerAuth`.

Коды ошибок (`400/401/403/404/409/500` с `Error { code, message }`) остаются как есть. Вне
списка трека — решения исполнителя, отмечаются в PR; черновик правки стоит показать исполнителю
backend#41 до мержа:

- в inline-enum `Error.code` добавляется `s2s_forbidden`, `csrf_invalid` остаётся: Go держит
  совместимость с текущим клиентом;
- у всех операций добавляется ответ `403` с описанием «S2S-ключ не принят» (у auth-ручек он
  заменяет описание «CSRF-токен не прошёл проверку»). Так статус есть в типах Orval-клиента;
- у refresh и logout добавляется `400` на неверное тело. Отозванный или чужой refresh — `401`
  с `Error`, как у остальных ручек.

Пока backend#41 не обновил Apidog, `bun run sync` вернул бы старый контракт и сломал бы BFF.
Поэтому в раздел «Источники» `AGENTS.md` добавляется временная оговорка: `spec/openapi.json` правлен
вручную по frontend#2, `sync` не запускать до backend#41.

После правки запускается только `bun run orval`. `bun run generate` **не запускается**: он
перегенерировал бы `apps/client/src/api/schema.ts` под новый контракт и сломал бы действующий
клиент (см. анти-цели). Расхождение спеки и клиентской схемы до #5 — ожидаемое, это пишется в PR.

## Решения исполнителя

Их стоит проверить на ревью.

- **Заглушка Go для приёмки.** Настоящего Go с целевым контрактом нет, поэтому сценарии приёмки
  прогоняются против заглушки: `apps/bff/dev/go-stub.ts`, сервер на `Bun.serve`, в памяти. Она
  реализует ручки из таблицы роутера по целевому контракту, принимает Bearer, проверяет
  `X-BFF-Key`, если он задан, и отвечает `403 s2s_forbidden`. Срок access задаётся переменной,
  чтобы проверить refresh за секунды. Счётчик вызовов `/auth/refresh` и ручки для сценариев сбоя
  (5xx, задержка дольше таймаута, отказ refresh, S2S) доступны только во внутренней сети Compose.
  Это инструмент разработки: в образ BFF заглушка не попадает. Интеграционную проверку с
  настоящим Go проводят после backend#41, отдельно от этой задачи.
- **`X-BFF-Key`.** Необязательная переменная `BFF_KEY`: если она задана, BFF ставит заголовок на
  каждый вызов Go, если нет — не ставит (одна VPS). В таблице переменных
  [«Сервиса»](https://docs.cellestial.ru/modules/2/tracks/bff/service#переменные-окружения) её нет,
  поэтому страницу трека правят отдельным PR в `docs` со строкой `Part of
  Cringe-Driven-Development-Team/frontend#2`. Значение ключа не логируется.
- **Таймауты.** Вызов Go обрывается через 5 с (`AbortSignal.timeout`). Graceful shutdown ждёт
  текущие запросы до 10 с, `stop_grace_period` в локальном Compose — 15 с.
- **Сервер.** `Bun.serve({ port, fetch: app.fetch })` с сохранённым `server`: на SIGTERM/SIGINT
  `server.stop()` перестаёт принимать запросы, по истечении срока — `server.stop(true)`. Вариант
  `export default { port, fetch }` из трека не даёт управлять остановкой.
- **Что экспортирует пакет.** `@cdd/bff` экспортирует `./src/types.ts`, где только
  `export type { AppRouter, BootstrapData }`. `index.ts` при импорте запускает сервер, поэтому
  точкой экспорта он быть не может.
- **Публичные файлы.** У клиента сейчас нет `public/`: favicon встроен в бандл. Явный список — это
  константа в BFF (сейчас пустая) и тот же список в упаковке образа. Файлы лежат в
  `/app/client/public/`, BFF читает их при старте; отсутствующий файл из списка запрещает старт.
  URL запроса файл не выбирает.
- **Путь шаблона** — `/app/client/index.html` по умолчанию. Для локального запуска без Docker
  путь переопределяет переменная `HTML_TEMPLATE`.
- **Упаковка образа** — корневой скрипт `bun run image`: `turbo run build`, затем
  `docker build -f apps/bff/Dockerfile .`. Это не turbo-задача пакета BFF, поэтому цикла
  `bff#build` → `client#build` нет. Образ — `oven/bun:<точная версия>-alpine`, пользователь `bun`,
  `HEALTHCHECK` через `wget`.
- **Локальный Compose** — `apps/bff/compose.yml`: сервис `bff` из собранного образа и сервис
  `go-stub` (`oven/bun`, монтирует заглушку). `APP_ORIGIN=http://localhost:3000`, порт публикуется
  только на `127.0.0.1`. Приёмка идёт через `curl`, а он отправляет `Secure`-cookie на
  `http://localhost`, поэтому локальный HTTPS не нужен и атрибуты cookie не ослабляются.
- **Новые зависимости** `apps/bff`: `hono`, `@trpc/server@11`, `zod`, `serialize-javascript` и его
  типы. Так же, как Orval в #45, это исключение из правила `AGENTS.md` о сторонних библиотеках:
  их требует сама задача.
- **Автотестов нет** — по приёмке задачи. Проверка ручная, по сценариям: команды и результаты
  попадают в описание PR. `bun run check` и `bun run build` должны проходить.

## Порядок работы

`AGENTS.md` требует работать этапами: после каждого этапа человек проверяет результат и даёт
команду на следующий.

1. Правка `spec/openapi.json`, `bun run orval`, заглушка Go.
2. Каркас: env, проверка шаблона и маркер в `apps/client/index.html`, `/health`, маршрутизация,
   JSON-логи, graceful shutdown.
3. Общий слой: шифрование cookie, сессия, клиент Go (Bearer, `X-BFF-Key`, `X-Request-ID`,
   таймаут), refresh с объединением и одним повтором после 401.
4. tRPC: `createContext` с CSRF, процедуры, перевод ошибок, `errorFormatter`, экспорт типов.
5. HTML-хендлер с bootstrap и HTML 503.
6. Dockerfile, `bun run image`, локальный Compose, прогон сценариев приёмки, раздел про BFF в
   `docs/local-development.md`.

## Что остаётся исполнителю

Раскладка файлов внутри `apps/bff/src` (кроме того, что задано треком), имена внутренних функций,
формат ручек заглушки для сценариев сбоя, точная версия образа Bun, как именно проверить
сохранение маркера в сборке Vite.
