# Статусы задач и уведомления о выпуске — frontend#101

Дата: 2026-11-01. Задача: <https://github.com/Cringe-Driven-Development-Team/frontend/issues/101>.
Статус: согласован переходом к `superpowers:writing-plans`; реализация ещё не начата.

## Цель и согласованные решения

Команда различает закрытие issue при мерже, готовность выпуска и успешную выкатку.
После публикации обоих проверенных артефактов карточка получает `Ready for release`,
после успешной выкатки — `Done`. Сами issues остаются закрытыми.

Пользователь согласовал:

- Отдельный workflow синхронизации после CI/CD, который можно повторить без
  сборки, публикации и доступа к VPS.
- При первом запуске подхватить уже опубликованные, но ещё не выкаченные задачи.
  Всё, что уже входило в успешную выкатку, оставить в `Done`.
- Успешная выкатка учитывается навсегда: последующий откат не возвращает задачи
  в `Ready for release`.
- Если полный список PR превышает лимит сообщения Telegram, в одном сообщении
  показываем количество PR и ссылку «Все PR выпуска» на полный отчёт Actions.
  Обычно все PR со ссылками остаются прямо в сообщении.

Решения ниже о конкретных API, журнале уведомлений, начальной границе сообщений
и обработке ошибок предложены автором дизайна и входят в его согласование.

## Approaches

1. Обновлять доску шагами внутри CI/CD. Это требует меньше отдельных workflows,
   но ошибка доски смешивается с результатом выпуска или выкатки.
2. Отдельный workflow после CI/CD. Ошибка синхронизации видна отдельным запуском;
   повтор не публикует артефакты и не переключает BFF. Добавляется один workflow.

Выбран второй подход. Он использует существующие GitHub Deployments, Bun и
TypeScript. Новых сервисов и зависимостей нет.

## Текущее состояние и границы

Исходная проверенная ревизия frontend/main: `55fd3616c174d014a49fd8e1162d7073dcf3b17c`.

- `ci.yml` публикует ассеты S3/CDN и публичный образ GHCR. Только после проверки
  обоих `register()` создаёт успешный `release-artifacts` Deployment с SHA,
  `image_ref`, `assets` и `ci_run`.
- `cd.yml` создаёт `production` Deployment для выбранного SHA. `success`
  записывается после health check, до retention. Поэтому общий красный CD
  после ошибки retention не отменяет успешную выкатку.
- Аналогично ошибка course-sync может сделать CI красным после готовности выпуска.
- `auto_inactive: false` сохраняет историю успешных выкаток и публикаций.
- В Scrumban №1 статусы расположены в нужном порядке; фильтры `sprint:@current`
  и `sprint:@next` уже существуют. Их не изменяем.
- В `.github/CONTRIBUTING.md` пока написано, что карточка после мержа уезжает в `Done`.

Работа не меняет сборку, проверку артефактов, Ansible, переключение BFF, выбор
цели rollback, backend, закрытие issues и ручные этапы тестирования. Настройка
автоудаления веток и перенос target зависимых PR — отдельное штатное поведение
GitHub; дополнительная автоматика для него здесь не нужна.

## Workflow и доверенные данные

Один новый `.github/workflows/release-status.yml` содержит независимые обработчики:

- `workflow_run: completed` для существующих `CI`, `CD` и `Rollback`;
- `workflow_dispatch` из `main` для первого запуска и повторной синхронизации;
- `pull_request_target: enqueued` для очереди PR в `main`.

Очередь обслуживает отдельный обработчик этого же файла. Каждый допустимый
запуск сверяет и карточки, и все ещё не обработанные уведомления, а не только
событие, которым его запустили. Это важно для вытесненных ожидающих запусков.
Для событий завершения принимаются только запуски этого frontend-репозитория:
CI — `push` в `main`; CD/Rollback — `workflow_dispatch` из `main`. Дополнительно
проверяются ID/path исходного workflow через Actions API. PR CI, форки и
`merge_group` не являются подтверждением публикации или выкатки.

Общий `conclusion` исходного workflow не является условием продвижения:
нужен соответствующий успешный Deployment с корректным payload и ссылкой на
доверенный run. Выбранный SHA CD берётся из Deployment, а не `workflow_run.head_sha`:
человек мог выкатить старый выпуск, запустив актуальный workflow из `main`.

`deployment_status` не используется как триггер: записи создаются через
`GITHUB_TOKEN`, а такие события не запускают последующие workflows.
Каждая синхронизация заново читает всю подходящую историю, включая пропущенные
запуски. Если новый ожидающий run вытеснит старый в concurrency, информация не теряется.

Исполняется только код актуального `main`, checkout с полной историей и
`persist-credentials: false`. Код и артефакты из PR/`workflow_run.head_sha`
не исполняются. Для очереди тоже явно checkout `main`, а не head PR.
Названия, ссылки и тексты из GitHub передаются как данные и экранируются для Telegram.

Репозиторный `GITHUB_TOKEN`: `contents: read`, `actions: read`,
`pull-requests: read`, `issues: read`, `deployments: write`.
`ADD_TO_PROJECT_PAT` применяется отдельно только к Project API. В начале
проверяются доступ к Scrumban, `viewerCanUpdate`, поле `Status` и нужные options;
фактическая mutation проверяется при интеграционной приёмке.
Секреты production, S3 и SSH синхронизации не нужны. Telegram использует
существующие bot/chat/topic настройки.

## Состав выпуска и связанные задачи

`P(R)` — множество уже merged PR командного frontend, чей `merge_commit_sha`
достижим из полного SHA выпуска R. Состав определяется по графу Git, например
`git merge-base --is-ancestor`, и метаданным GitHub, а не по строкам merge-коммитов,
номеру PR, одному `head_sha` или времени мержа. В текущем репозитории разрешены
только merge commits; поддержку дополнительных методов мержа не добавляем.

Список merged PR и все API connections читаются с пагинацией. Фильтр только
`base=main` не применяется: вложенный PR, фактически вошедший через другой PR,
также входит в выпуск. PR, влитый в старую ветку и ещё не достижимый из R,
не входит. Кандидат merge queue ещё не merged и не входит.

Связи PR с задачами берутся из `closingIssuesReferences`, не из произвольных
упоминаний. Для изменения карточки issue должна:

- принадлежать `Cringe-Driven-Development-Team/frontend`;
- иметь заголовок с префиксом `Frontend.` или `BFF.`;
- быть закрыта как completed мержем включённого PR: это подтверждает последний
  `ClosedEvent.closer` типа PullRequest;
- иметь существующую карточку именно в Scrumban №1.

Ссылки в `Part of`, задачи других репозиториев, закрытые вручную/not planned,
открытые или переоткрытые issues не изменяются. Одна issue учитывается один раз.
Отсутствующая карточка подходящей задачи — видимая ошибка, новую не создаём.

Определим множества PR:

- `Published` — объединение `P(R)` всех корректных успешных `release-artifacts`.
- `Deployed` — объединение `P(D)` всех корректных успешных `production` за всю
  историю, включая предыдущие выкатки и успешные откаты.

Только успешные Deployments учитываются. Ошибка, незавершённая попытка,
частично залитые артефакты и отметки журнала уведомлений ничего не продвигают.

## Переходы карточек и гонки

Синхронизация меняет только `Status`, не issue, sprint, assignees или другие поля.

| Условие                                | Текущий Status      | Результат                     |
| -------------------------------------- | ------------------- | ----------------------------- |
| Закрывший PR в `Deployed`              | `Ready for release` | `Done`                        |
| Закрывший PR в `Deployed`              | `Done`              | Без записи                    |
| PR в `Published`, но не в `Deployed`   | `Done`              | `Ready for release`           |
| PR в `Published`, но не в `Deployed`   | `Ready for release` | Без записи                    |
| Любое другое условие или ручной статус | любой               | Без изменения, причина в логе |

Под ручными статусами здесь понимаются значения вне `Done` и `Ready for release`,
включая три этапа тестирования/сборки. Эти два значения управляются по таблице
независимо от автора последней записи: вручную выставленный `Done` для ещё не
выкаченной задачи тоже будет исправлен на `Ready for release`. Происхождение
каждого ручного переключения отслеживать не требуется.

Первый запуск выполняет те же правила: старые выкаченные задачи не проходят
обратно через `Ready for release`. Успешный старый SHA продвигает только свой
состав; задачи более нового выпуска остаются ждать. Откат не уменьшает `Deployed`.

Перед первым переходом `Done → Ready for release` дождаться завершения закрытия
issue и автоматического `Done`. Проверяются закрытие и последнее обновление
значения Status: `Done` должен быть подтверждён не раньше текущего `ClosedEvent`.
Проверка повторяется с ограничением 5 минут; таймаут или невозможность подтвердить
порядок даёт ошибку без записи. Ручные статусы не перезаписываются. При уже
установленном `Ready for release` повторно ждать `Done` не нужно.

Если связанная с только что merged PR issue ещё не закрылась, это тоже ожидание
в пределах тех же 5 минут. Явное переоткрытие после мержа прекращает ожидание:
такую задачу пропускаем, issue самостоятельно не закрываем.

Весь workflow имеет общую concurrency-группу без отмены идущего, включая
инициализацию и уведомления. Каждый запуск читает накопившиеся события для всех
подходящих PR: замена ожидающего run событием другого PR ничего не теряет.
Перед изменением перечитываются issue и Status: переоткрытую issue не трогаем.
Перед записью `Ready for release` заново проверяется история production. После
пакета записей сверяется, не появились ли новые успешные Deployments; если появились,
расчёт повторяется по свежей истории. Это устраняет устаревший снимок, если CD
завершился во время синхронизации. Число повторов ограничено; при исчерпании —
красный run и безопасный ручной повтор. Новый `workflow_run` также повторит расчёт.

## Четыре уведомления

### Постановка PR в очередь

По реальному `enqueued` для `main`: «PR #N поставлен в очередь» со ссылкой.
Позиция и номер очереди не обещаются. `merge_group` не отправляет сообщение.
Bypass без очереди не создаёт события и сообщения.

Ключ — ID `AddedToMergeQueueEvent` в timeline PR, а не SHA, номер PR или run.
Обработчик читает все ещё не обработанные события этой очереди после включения
автоматики, поэтому удаление и повторное добавление PR дают два различных ключа,
а повтор run не создаёт дубликат. Общая concurrency всего workflow и чтение
timeline всех PR, обновлённых после границы включения, компенсируют вытеснение
ожидающего run. Учитываются и уже merged/closed PR, успевшие выйти из очереди.
Недоступную/ещё не появившуюся timeline ограниченно перечитываем; затем ошибка.

### Выпуск готов

Успешное сообщение «Релиз фронта залит, ждёт выкатки» переносится из job publish
в синхронизацию. В CI сохраняется уведомление об ошибке публикации; готовность
не объявляется по одному артефакту или общему зелёному Check.

На один SHA — одно сообщение с полным SHA, digest, ссылкой на CI и полным списком
впервые вошедших PR со ссылками. Выпуски упорядочиваются по первому успешному
статусу публикации, при равенстве — по ID Deployment. Список R равен `P(R)` минус
PR из всех ранее опубликованных выпусков. Повторные записи одного SHA объединяются.
Пропущенная публикация не попадает в это вычитание: следующий выпуск перечислит
накопившиеся PR. Для выпуска без новых PR это прямо указано в сообщении.

Каждый обработанный выпуск получает полный Markdown-отчёт в Actions job summary:
SHA, исходный CI, Deployment и все PR со ссылками. Telegram проверяется по длине
видимого текста после разбора HTML entities. Если полный список вместе с остальными
строками не помещается в 4096 символов, сохраняем одно сообщение: полный SHA,
digest, количество PR и ссылку «Все PR выпуска» на этот отчёт. Произвольный
обрезанный фрагмент списка не показываем. Ссылка ведёт на run синхронизации,
создавший отчёт, и сохраняется в журнале вместе с текстом уведомления, чтобы
повтор не ссылался на отсутствующий отчёт другого запуска.

Список и исходные ссылки сохраняются при первой обработке в журнале уведомления;
повтор не пересчитывает уже зафиксированный текст. Ошибка доски не скрывает готовность:
отправка уведомления и изменение карточек — отдельные результаты, обе операции
пытаемся выполнить, затем общий run остаётся красным при ошибке любой из них.
Подготовка отчёта/записей `pending` и отправка выполняются разными шагами workflow:
Actions загружает summary завершённого шага до начала шага отправки. Поэтому
ссылка на полный отчёт появляется до сообщения Telegram. Шаг отправки запускается
и после ошибки доски, если проверка доверия к исходному событию прошла.

Первое включение молча учитывает старые публикации для расчёта состава, без
массовой повторной рассылки старых сообщений. Граница — дата main-коммита,
который впервые добавил этот workflow в main, а не начало первого обработчика.
Коммит находится по first-parent истории main и добавлению файла workflow;
граница фиксируется один раз в служебном Deployment и затем не меняется.
События с createdAt/первым успешным статусом не раньше границы считаются новыми:
публикация или enqueue, запустившие первый run, не поглощаются и уведомляются.
Более ранние публикации подавляются только для рассылки, их PR учитываются
в составе и первом обновлении доски. Последующие новые публикации уведомляются.
Если запоздало обработанный SHA уже входил в успешную выкатку, сообщение
«ждёт выкатки» для него не отправляется; причина остаётся в журнале.
Это проверяется и перед доставкой ранее подготовленного pending сообщения:
если CD успел завершиться, receipt погашается состоянием `inactive` с причиной
`already_deployed`. Проверяется достижимость самого SHA, а не только его PR:
новый коммит без новых PR тоже может ещё ждать выкатки. Неоднозначный
`in_progress` всё равно требует ручной проверки прошлой доставки.

### Начало выкатки

В `cd.yml`, после готового выпуска, создания production Deployment и подготовки
SSH/Vault, непосредственно перед `Switch BFF`, отправляется:
«Выкатка релиза <полный SHA> началась», инициатор и ссылка на текущий Actions run.
При повторном запуске workflow используется `GITHUB_TRIGGERING_ACTOR`, иначе
`GITHUB_ACTOR`. Шаг выполняется один раз на фактическую попытку переключения.
Ожидание environment/concurrency и ранний сбой не отправляют стартовое сообщение.
Ошибка Telegram видна, но `continue-on-error: true` позволяет продолжить CD.

### Итог выкатки

Существующее итоговое уведомление CD и диагностика этапов сохраняются в CD,
с `if: always()` и выбранным SHA. Его результат не подменяется ошибкой доски
из отдельного workflow. Отмена остаётся отдельным исходом, как сейчас.
Уведомления rollback сохраняются; стартовое сообщение этой задачи относится к CD.

## Журнал уведомлений и границы повторяемости

Для дедупликации используется отдельное непроизводственное окружение Deployments
`release-automation`, не S3, cache, issues/comments или новый сервис.
Оно не учитывается при выборе готового выпуска, цели отката и retention.

Payload служебной записи содержит вид события (`baseline`, `queue`, `ready`),
уникальный ключ, исходный run/event, зафиксированный список PR и ссылку на
полный отчёт для готового выпуска.
Ref — проверенный коммит frontend; для события очереди достаточно SHA доверенного
`main`, ключом остаётся ID события. Успешные статусы имеют `auto_inactive: false`.

Для каждого ключа: отсутствие записи → создать payload и `pending`; перед
отправкой поставить `in_progress`; после подтверждения Telegram (`ok: true`)
поставить `success`, сохранить message_id в описании статуса. При `success`
повтор ничего не отправляет. Все отправители одного типа/ключа сериализованы.
На первом запуске `baseline` создаётся до обработки очереди и публикаций;
завершённая граница затем не меняется.

Если runner упал между отправкой Telegram и записью `success`, невозможно
атомарно доказать доставку средствами этих двух API. Незавершённый `in_progress`
не пересылается автоматически: run красный, в логах ключ, служебный Deployment
и инструкция проверить тему Telegram. Если сообщение есть, оператор отмечает
запись успешной через Deployment Status API; если его нет — возвращает в `pending`
и повторяет синхронизацию. Явный подтверждённый отказ Telegram тоже можно повторить;
сетевой таймаут считается неопределённым результатом. Скрытого обещания exactly-once нет.

## Область изменений

- Новый workflow и команды синхронизации в `scripts/release/`, без нового пакета.
- Общий GitHub helper дополняется нужными REST/GraphQL запросами и пагинацией;
  существующие проверки payload/SHA и обработка ошибок сохраняются.
- `notify.ts` переиспользует HTML-экранирование, Telegram-настройки и формат сообщений;
  добавляются очередь/начало/список PR. Повторять транспорт в новом модуле не нужно.
- `ci.yml`: успешное сообщение переносится, уведомление об ошибке сохраняется.
- `cd.yml`: добавляется только стартовое сообщение перед `Switch BFF`.
- Тесты состава, карточек, журнала, уведомлений и разрешённых событий workflow.
- `docs/release.md`: статусы, четыре события, первый запуск, повтор и диагностика.
- Короткий документационный PR в `.github/CONTRIBUTING.md` объясняет закрытую issue
  и дальнейшие статусы выпуска. `Part of https://github.com/Cringe-Driven-Development-Team/frontend/issues/101`;
  он вливается первым. Frontend PR содержит `Closes #101` и вливается последним.

## Проверка и приёмка

Локальные тесты используют реальный Git-граф во временном репозитории и mock API;
проверяются наблюдаемые запросы и сообщения. Обязательные сценарии:

1. Два PR в выпуске, отсутствующая промежуточная публикация, вложенный PR и
   PR, чьи изменения ещё не достижимы из выпуска; пагинация API.
2. Первый запуск: опубликованное без выкатки → `Ready for release`;
   уже выкаченное остаётся `Done`; исторические сообщения не пересылаются.
3. Успешный Deployment при красном CI/course-sync либо CD/retention;
   выбранный SHA CD отличается от SHA workflow. Без корректного успеха продвижения нет.
4. Старый SHA выкатывается после нового, rollback, запоздавший CI, повтор runs,
   CD завершается во время синхронизации; итоговые статусы не регрессируют.
5. Задержанное закрытие/автоматический Done, таймаут, ручной статус, переоткрытие,
   чужой repository/project/title, ручное закрытие и отсутствующая карточка.
6. Два отдельных enqueue, повтор merge_group, dequeue/re-enqueue одного PR,
   повтор обработки, задержанное чтение timeline и bypass.
7. Нет готового сообщения при одном артефакте; SHA/PR-ссылки экранированы.
   Полный список, помещающийся в 4096 видимых символов, остаётся в сообщении;
   при превышении — одно сообщение с количеством и рабочей ссылкой на полный
   отчёт. В отчёте присутствуют все PR, без обрезания.
8. Start стоит непосредственно перед Switch, ранний сбой/ожидание не шлют его,
   отказ Telegram не блокирует Switch, итоговое уведомление сохраняется.
9. Повтор после success не шлёт сообщение; неоднозначный сетевой исход требует
   видимого ручного разрешения; подтверждённый отказ можно повторить.
10. Сбой Project API виден в отдельном run и не запускает повторный CD.

Перед завершением реализации: `bun run check`, `bun run test`, `bun run build`.
Затем в PR приложить реальные runs, Deployments, связанные PR/issues и состояние
карточек до/после. Проверить запись Status именно через `ADD_TO_PROJECT_PAT`.
Живой сценарий первого запуска и публикации/выкатки проверяется после появления
workflow в `main`; PR не объявляет эти проверки уже выполненными по одним mock-тестам.

Свободой исполнителя остаются разбиение функций/файлов, размер API страниц,
интервалы опроса в заданных пределах и детали тестовых fixtures. Изменение
наблюдаемого поведения, состава задач или гарантий уведомлений требует правки дизайна.
