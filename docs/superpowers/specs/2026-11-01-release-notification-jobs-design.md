# Независимая доставка уведомлений и обновление доски

Задача: [frontend#133](https://github.com/Cringe-Driven-Development-Team/frontend/issues/133).
PR: [frontend#134](https://github.com/Cringe-Driven-Development-Team/frontend/pull/134), ветка `web-133`.
Статус: спецификация подтверждена владельцем.

## Цель и границы

Алерты «PR поставлен в очередь» и «Релиз залит, ждёт выкатки» должны отправляться
без ожидания сверки Scrumban. Сейчас общий последовательный обработчик заставляет
их ждать историю, карточки и предыдущий проход доски. В последнем запуске это
добавило примерно девять минут после CI.

Расширяем текущую задачу и PR; исправление утечки тестового `GITHUB_STEP_SUMMARY`
сохраняется. Сам обход доски и механизм CD/Rollback не оптимизируем. Формат сообщений,
граница включения автоматики, статусы карточек и правила доставки сохраняются.

## Подходы

- Выбран владельцем: две независимые jobs в существующем `Release status`.
  Общая точка ручного запуска сохраняется, ошибки и ожидание доски не задерживают алерты.
- Два отдельных workflow: более явное разделение в Actions, но дублирование настроек
  и проверок источника. Этот вариант не выбран.

## Две независимые работы

- `notifications`: обработка источника, подготовка отчёта и доставка. Собственная
  группа concurrency, `cancel-in-progress: false`. Только эта job создаёт baseline,
  готовит уведомления и меняет журнал доставки; несколько её запусков не отправляют
  один ключ параллельно. Project PAT этой job не передаётся.
- `board`: проверка источника и прежняя синхронизация карточек. Отдельная группа
  concurrency, `cancel-in-progress: false`. Запускается после CI/CD/Rollback и вручную;
  на enqueue не запускается. Получает Project PAT, но не Telegram token и не пишет
  журнал уведомлений.
- Между jobs нет `needs`, общего workflow-level concurrency или ожидания результата
  другой job. Ошибка одной не отменяет другую. Обе используют доверенный `main`,
  без исполнения head PR. Проверки репозитория, ref, события и Actions run сохраняются.

## Уведомления

- На enqueue первым обрабатывается исходный PR: его действительное событие очереди
  проверяется по GitHub timeline, готовится и отправляется сообщение. Для этого не
  читаются задачи, Project API, история публикаций и production. Последующее
  подхватывание пропущенных событий очереди может читать другие PR/timeline, но не доску.
- После завершения CI готовность определяется по успешному `release-artifacts`,
  совпадающему SHA и проверенному исходному CI run; общий красный CI из-за course-sync
  не отменяет подтверждённую публикацию. Состав PR и Summary сохраняются.
- Подготовка и отправка ready не вызывают полный `readReleaseSnapshot`: закрывающие
  связи задач и их состояния для этого сообщения не нужны. Читается необходимая
  история публикаций, PR и production; production-записи без контракта BFF
  отбрасываются до дополнительных запросов их статусов.
- Текущее событие получает приоритет перед восстановлением старых событий.
  Enqueue отправляет queue-сообщения, без обхода pending ready и их проверок production.
  Последующие CI/ручные запуски подхватывают пропущенные публикации и события очереди;
  вытесненный ожидающий запуск не должен означать потерю события.
- Перед отправкой ready сохраняется подавление выпуска, уже входившего в успешную
  выкатку, включая историю до rollback. Проверка не читает карточки или полный каталог задач.
- Сохраняются ключи `queue:<event ID>` и `ready:<SHA>`, исходный payload и переходы
  pending → in_progress → success. Подтверждённый отказ Telegram допускает повтор;
  неизвестный исход и ошибка записи success после доставки требуют ручной проверки.
- Summary публикуется отдельным шагом до отправки сообщения со ссылкой на него.
  Ошибка Project API не влияет на подготовку и отправку уведомлений.

Решения о единственном писателе журнала, приоритете текущего события и раздельной
обработке видов pending предложены агентом для сохранения прежней защиты от дублей.
Время выделения runner и очередь других уведомлений остаются ограничениями GitHub;
жёсткое обещание доставки за фиксированное число секунд не вводится.

## Проверка

На HTTP boundary доказать доставку enqueue без запросов задач/истории выкаток;
доставку ready при недоступном Project API; отсутствие зависимости jobs и общей
блокировки; сохранение доверенного источника, всех страниц состава, baseline,
подхвата вытесненных событий, дедупликации и неоднозначных исходов Telegram.
Сохранить регрессионную проверку неизменности унаследованного CI Summary.

Перед PR: `bun run check`, `bun run test`, `bun run build`, actionlint изменённых
workflows. Никаких реальных сообщений, мержа или CD при локальной проверке.
