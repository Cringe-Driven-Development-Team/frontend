# Упоминания инициатора релизов — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Во всех существующих уведомлениях о заливке, выкатке и откате фронтенда упоминать инициатора в Telegram через существующую карту пользователей.

**Architecture:** `notify.ts` форматирует инициатора по необязательной карте `TELEGRAM_USER_MAP`, сохраняя обычный логин при некорректной настройке. Четыре шага релизных workflow передают repository variable в окружение команды. Тесты проверяют исходящие API-запросы и фактическую структуру workflow.

**Tech Stack:** TypeScript, Bun 1.4.x (`bun:test`, `Bun.YAML`), GitHub Actions, Telegram Bot API с HTML-разметкой. Локальный Bun: 1.4.2.

**Spec:** [Утверждённая спека](../specs/2026-10-13-release-telegram-mentions-design.md), утверждена пользователем 13.10.2026. Исполнитель и ревьюер читают оба документа.

## Review Focus

Пять дополнительных случаев включены в тесты задачи 1:

1. Карта содержит валидного инициатора и испорченную запись другого человека: правильное упоминание сохраняется.
2. Регистр ключа отличается от `GITHUB_ACTOR`: используется обычный логин, без нечаянного выбора другого соответствия.
3. Большой ID записан строкой: цифры сохраняются без потери точности; то же значение как небезопасное JSON-число отвергается.
4. Повторный запуск задаёт иной `GITHUB_TRIGGERING_ACTOR`: получателем остаётся пользователь из `GITHUB_ACTOR`.
5. Telegram отвечает HTTP 400 или `fetch` отклоняется: прежняя ошибка отправки сохраняется, fallback карты её не поглощает.

## Исполнение после проверки плана

Рекомендуется **subagent-driven-development**: последовательный исполнитель и отдельное ревью для formatter, затем для подключения workflow, затем финальная сверка со спекой. Два самостоятельных результата требуют разного внимания: обработка входной карты и полнота передачи настройки во всех ветках уведомлений.

Альтернатива — **executing-plans**: контроллер сам выполняет обе задачи и получает независимое финальное ревью. Реализация начинается после утверждения плана и выбора способа исполнения пользователем.
