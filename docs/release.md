# CI, синхронизация и выкатка фронтенда

## Рабочий репозиторий и учебная копия

Разработка и ревью проходят в [командном frontend](https://github.com/Cringe-Driven-Development-Team/frontend).
[Учебный репозиторий](https://github.com/frontend-park-mail-ru/2026_2_Cringe_Driven_Development)
получает те же коммиты `main`; его Actions выключены, PR и ревью туда не копируются.

Синхронизация включается переменной `COURSE_SYNC_ENABLED=true` после Check,
независимо от Publish release. Повторить её без выкатки: Actions → Sync to course,
ветка main, `ci_run_id` успешного push/main CI. Произвольный SHA не принимается.
Publish release, CD и Rollback доступны только в командном репозитории из main
при `PRODUCTION_ENABLED=true`. Отсутствующий flag означает выключенную операцию.
Порядок первого включения и отката — в
[runbook организации](https://github.com/Cringe-Driven-Development-Team/.github/blob/main/docs/migrations/team-repositories-runbook.md).

Если локальный клон всё ещё указывает на учебную копию, переключите remote:

```bash
git remote set-url origin https://github.com/Cringe-Driven-Development-Team/frontend.git
git fetch origin
git remote -v
```

## Выкатка

Выпуск коммита `main` — два артефакта одного SHA: ассеты клиента (JS, CSS, неперсональный
`index.html`) в S3 и на CDN в неизменяемом `releases/<sha>/` и **публичный** образ BFF в GHCR с
серверным бандлом и HTML того же коммита. На прод выкатывается образ по digest: HTML отдаёт
работающий BFF, S3-указателя и копии корневого `index.html` больше нет. Готовые выпуски и история
прода хранятся в GitHub Deployments. Шаги — команды `scripts/release/` (`bun run release <команда>`).

| Workflow   | Когда                                                 | Что делает                                                                                                                                                                                                                                                                                                                                                 |
| ---------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CI`       | pull request, Merge Queue и push в `main`             | `bun run check`, `bun run test`, `bun run build` — без production-секретов. На push в `main` ещё job `Publish release`: сборка с `RELEASE_SHA` и CDN base → заливка `releases/<sha>/` (неизменяемо) → Release check → образ BFF `sha-<sha>` в GHCR → анонимная проверка digest → запись `release-artifacts`; готовое сообщение отправляет `Release status` |
| `CD`       | вручную из `main`, вход `sha` (пусто — голова `main`) | готовый выпуск SHA → анонимная проверка образа → Release check → запись `production` → Telegram о начале → `deploy-bff.yml` из infra → Health check → итог записи → retention → Telegram                                                                                                                                                                   |
| `Rollback` | вручную: `Actions` → `Rollback` → `Run workflow`      | цель по истории `production` → те же проверки и тот же `deploy-bff.yml` → итог записи → Telegram                                                                                                                                                                                                                                                           |

`Release status` независимо обновляет доску и уведомления после CI/CD/Rollback,
при постановке PR в очередь и по ручному запуску; он не собирает и не выкатывает приложение.

### Готовые выпуски: `release-artifacts`

Job `Publish release` работает в environment `production` (ключ S3), но с
`environment.deployment: false`: заливка в CDN ещё не означает, что выпуск работает на VPS. Вместо
автоматической записи после проверки **обоих** артефактов скрипт создаёт явный Deployment:

| Поле          | Значение                                                                                                                                 |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `environment` | `release-artifacts`, `production_environment: false`                                                                                     |
| `ref`         | полный SHA коммита                                                                                                                       |
| `task`        | `publish`                                                                                                                                |
| `payload`     | `{ "image_ref": "ghcr.io/cringe-driven-development-team/bff@sha256:…", "assets": "releases/<sha>/", "ci_run": "<ссылка на запуск CI>" }` |
| статус        | `success` с `auto_inactive: false`: успех прежних выпусков не становится `inactive`                                                      |

Успешная запись на SHA одна. Повторный CI того же SHA её находит и ничего не пересобирает; другой
digest того же SHA отклоняется. Ассеты неизменяемы: уже залитый релиз сверяется с новой сборкой
побайтно и не перезаписывается. Частично опубликованный выпуск (нет записи `success`) в CD не
попадает. Отдельного `release.json` в S3 нет.

Образ: `ghcr.io/cringe-driven-development-team/bff`, тег `sha-<полный SHA>` — только для поиска (он
может быть перезаписан повторной публикацией), выкатывается digest. Метка
`org.opencontainers.image.revision` — полный SHA: по ней CD и Ansible сверяют образ с релизом.
Package `bff` должен быть **публичным**: VPS скачивает образ без GHCR credentials. Перед
регистрацией выпуска CI получает анонимный токен GHCR и читает манифест по digest; приватный
package — выпуск не готов, job красный. При первой публикации package создаётся приватным:
GitHub → Packages → `bff` → Package settings → Change visibility → Public, затем `Re-run failed jobs`.

### Выкатка и история прода: `production`

`CD` и `Rollback` тоже работают с `environment.deployment: false` и пишут историю сами
(`deployments: write`). До изменения сервера:

1. единственная успешная запись `release-artifacts` выбранного SHA → `image_ref` и каталог ассетов;
2. анонимная доступность точного digest и метка `org.opencontainers.image.revision` = SHA;
3. Release check: `index.html` и все JS и CSS из него отдаются с CDN, JS — с CORS; без любого ассета прод не меняется.

Затем создаётся запись `production` (`ref` — SHA **выбранного образа**, в том числе при откате;
`payload` — `image_ref`, `assets`, `action` = `deploy`/`rollback`, `run` — ссылка на этот запуск) со
статусом `in_progress`, и запускается `ansible/deploy-bff.yml` из
[infra](https://github.com/Cringe-Driven-Development-Team/infra) на зафиксированной ревизии
(`INFRA_REF` в workflow) с `bff_image_ref` и `bff_release_sha` — без GHCR credentials. Ansible скачивает
образ анонимно, сверяет метку, переключает BFF и Caddy, проверяет, что запущен именно этот образ и он
`healthy` (внутренний `/health`), и пробу снаружи. После него Health check workflow:

- `https://cellestial.ru/login` — ровно один `<script id="bootstrap">` с `{"user":null}`,
  `<meta name="release">` этого SHA, `Cache-Control: private, no-store`;
- JS и CSS из HTML — с CDN `releases/<sha>/` и отдаются (чанк — с CORS);
- `users.me` без сессии — tRPC `UNAUTHORIZED` (401), `/api/unknown` — 404 не HTML.

Итог записи: `success` — только после всех проверок фактически запущенного выпуска; переключение было,
а проверка не прошла — `failure`; сбой до проверки результата или отмена — `error`. Workflow при
этом красный, а не ложно успешный. Выкатить: `Actions` → `CD` → `Run workflow` из `main`, в `sha` —
полный SHA из сообщения о заливке, либо `gh workflow run cd.yml -f sha=<sha>`.

### Откат

`Rollback` выбирает цель по истории `production` в GitHub **до доступа к VPS**, не по `.env`, Telegram
или тегу:

- последняя завершённая попытка `success` → предыдущий успешный выпуск с **другим** digest;
- последняя попытка `failure`/`error` → последний успешный выпуск (восстановление);
- последняя попытка незавершённая или без статуса, цели нет или у SHA в истории разные digest →
  остановка до изменений.

Цель сверяется с успешной записью `release-artifacts` (тот же digest), затем те же проверки образа и
ассетов и тот же `deploy-bff.yml`. Последний успешный Deployment — последний подтверждённый
результат проверки, а не гарантия того, что контейнер работает сейчас: отсутствующий или упавший
контейнер откат не блокирует, а после запуска Ansible проверяет фактический образ, здоровье и API.
Откат возвращает HTML и ассеты цели без пересборки. `SESSION_KEY` берётся из Vault и одинаков у
выкатки и отката: действительные cookie сессии остаются читаемыми. **Откат BFF не откатывает Go и
БД**; совместимость миграций оценивается отдельно.

### Retention

После успешной выкатки `CD` оставляет в S3 пять последних релизов и, независимо от возраста, ассеты
последнего успешного выпуска прода и предыдущего успешного с другим digest. Если последняя попытка
выкатки не `success`, очистка откладывается до следующего подтверждённого результата: попытка могла
переключить контейнер. Ассеты выпуска, который сейчас публикуется или выкатывается, входят в пять
последних.

### Очередь

`CD` и `Rollback` (вместе с retention внутри `CD`) — одна группа `concurrency: production` без
отмены: идущая выкатка не прерывается следующим запуском. В группе один идущий и один ожидающий
запуск; более новый ожидающий вытесняет прежнего (он отмечен `cancelled`, прод не менялся).
Публикации одного SHA сериализуются группой `publish-<sha>`.

### Telegram

Четыре события приходят в существующую тему выкаток:

1. **«PR #N поставлен в очередь»** — одно сообщение на фактическое добавление PR
   в merge queue `main`. Позиции в очереди нет. Повтор `merge_group` не дублирует
   сообщение; удаление и повторная постановка PR создают новое событие. Bypass
   без очереди такого сообщения не создаёт.
2. **«Релиз фронта залит, ждёт выкатки»** — одно сообщение на проверенный SHA
   после успешного `release-artifacts`. В нём полный SHA, digest, CI и номера PR
   со ссылками, впервые вошедших в опубликованный выпуск. Если промежуточный CI
   не опубликовал выпуск, его PR перечислит следующая публикация. При превышении
   4096 видимых символов сообщение показывает количество и «Все PR выпуска» —
   ссылку на полный отчёт Actions. Кнопка «Выкатить» открывает ручной CD.
3. **«Выкатка началась»** — непосредственно перед `Switch BFF`, после проверок и
   подготовки SSH/Vault. Вместо SHA показаны названия входящих PR со ссылками;
   есть текущий инициатор и кнопка «Логи выкатки». Если PR несколько, выводится список,
   при переполнении — ссылка на полный отчёт Actions. Полный SHA остаётся в отчёте
   и итоговой карточке. Ожидание допуска/очереди и ранний сбой не создают сообщение.
4. **«Выкатка фронта: успешно/ошибка»** — итоговый результат CD с выбранным SHA;
   отмена остаётся отдельным исходом. Сохраняется и при ошибке после старта.

Готовое сообщение отправляет отдельный `Release status`, а CI сохраняет
уведомления об ошибке/отмене публикации. Начало и итог отправляет сам CD;
отказ Telegram на этих шагах виден в логах и не блокирует переключение BFF.

Сообщения приходят в топик `TELEGRAM_RELEASES_TOPIC_ID` (Frontend / Releases); инициатор
упоминается по `TELEGRAM_USER_MAP`. Карточка выкатки и отката показывает полный SHA, digest образа,
ссылку на запуск и названия связанных задач со ссылками вместо первых коммитов.
Общая задача нескольких PR показывается один раз; PR без закрывающей связи — под
своим названием. CD показывает добавленные PR между предыдущей и выбранной версиями,
Rollback — удалённые, в разделе «Отменённые задачи». При отсутствии PR это явно указано.

Для одного PR есть кнопка «PR», для 2–6 — «PR #N» по две в строке, для большего
количества — одна «Все PR выпуска». Полный список PR и их задач, полные SHA и сравнение
версий доступны в Summary текущего CD/Rollback run (`#summary`). Кнопка «Изменения» убрана.
Длинные названия и список в Telegram сокращаются в бюджете 4096 видимых символов,
полный отчёт сохраняет все записи. Ошибка GitHub отображается как «Состав изменений
недоступен»; она не превращается в пустой список и не скрывает итог выкатки.
При ошибке записи Summary данные в сообщении сохраняются, кнопки на отсутствующий
отчёт нет; если полный список нужен, выводится «Полный отчёт недоступен».

Слева в «Версии» — последний подтверждённый выпуск по истории GitHub Deployments.
`Health Check ✅` означает успешный шаг проверки текущего запуска, `❌` — провал,
`⚪` — проверка не выполнялась, отменена или результат неизвестен. Бейдж независим от
общего результата job: ошибка retention не отменяет успешный Health check. Этап сбоя
и сведения о неподтверждённом переключении при ошибке сохраняются. Это результат
проверки во время запуска, не постоянный мониторинг.

Кнопка «↩️ Откатить» лишь открывает workflow
Rollback — нажатие в Telegram прод не меняет. Сбой отправки сообщения не меняет результат уже
проверенной выкатки.

### Статусы задач и повтор синхронизации

GitHub issue закрывается мержем PR. После этого её карточка frontend/BFF
показывает готовность выпуска, а не состояние issue:

| Status              | Назначение                                                               |
| ------------------- | ------------------------------------------------------------------------ |
| `Ready for test`    | Ждёт проверки, выставляется вручную                                      |
| `In testing`        | Проверяется, выставляется вручную                                        |
| `Ready for build`   | Проверка завершена, ждёт релизной сборки; выставляется вручную           |
| `Ready for release` | Изменения вошли в проверенный выпуск и ещё не входили в успешную выкатку |
| `Done`              | Изменения уже входили в успешную выкатку                                 |

Ручные этапы не запускают и не блокируют CI/CD. Автоматика изменяет только
`Done`/`Ready for release` у закрытых мержем задач `Frontend.`/`BFF.` этого
репозитория в Scrumban №1; ручные значения вне этих двух сохраняются.
Issue не переоткрывается, Sprint и другие поля не меняются.

`Release status` запускается после CI/CD/Rollback, при enqueue и вручную.
Он читает проверенные Deployments и полный Git-граф, включая несколько PR в
выпуске и вложенные PR, фактически попавшие в SHA. Красный CI из-за course-sync
или CD из-за retention не отменяет успешный Deployment. Выбранный SHA CD может
отличаться от SHA кода workflow. Успех старого SHA затрагивает только его состав;
история всех успешных выкаток сохраняется, rollback не возвращает задачи назад.
Автоматические environment-записи без payload BFF не доказывают выкатку.

Перед переходом из `Done` обработчик ждёт закрытия и обновления автоматического
`Done` после события закрытия (до пяти минут). Переоткрытая задача пропускается.
После пакета обновлений повторно проверяется production: завершившаяся параллельно
выкатка имеет приоритет. Доска выполняется в job `Board`, в группе `release-board`. Она не запускается на enqueue.

Доставка выполняется отдельно в job `Notifications`, в группе `release-automation`.
Между jobs нет `needs` и общей workflow-level блокировки: ошибка или долгий проход
доски не задерживает отправку. Project PAT есть только у Board, Telegram token —
только у Notifications; журнал доставки меняет только Notifications.
С CD/rollback эти группы не совмещены.

Notifications сначала готовит и отправляет текущее событие. Для enqueue читается
только исходный PR/timeline и журнал, без tasks, Project API и истории выкаток;
доставляется только его ключ. Ready готовится по подтверждённым артефактам и
доверенному CI run, без чтения issues или Project API. Старые автоматические
production-записи без контракта BFF отбрасываются до запросов их статусов.
Затем recovery подхватывает остальные события: enqueue — только queue, после
CI/ручного запуска — также пропущенные публикации. Так вытеснение ожидающего run
не теряет события. Проверка уже выкаченного pending ready, дедупликация и
ограничения повторной доставки сохраняются.
При первом переходе незавершённый старый workflow ещё может удерживать существующую
группу Notifications; после его завершения ожидания доски больше нет.

Первый запуск подхватывает старые опубликованные, но не выкаченные задачи.
Уже выкаченные остаются в `Done`. Исторические сообщения не пересылаются:
граница — main-коммит, впервые добавивший `release-status.yml`, сохранённая
в служебном baseline. Публикация и enqueue не раньше этой границы уведомляются.

Отдельный красный `Release status` означает ошибку синхронизации/уведомлений,
а не повторную выкатку или отмену уже готового выпуска. Логи содержат SHA,
PR, issue, изменения и причины пропусков. Подготовка current/recover и соответствующая отправка — разные
шаги: Actions публикует summary до сообщения со ссылкой на него. Сбой подготовки
или доставки current не скрывает независимые сообщения recovery; общий результат
job при ошибке остаётся красным.
Для повторной попытки без доступа к VPS и без публикации артефактов:

```bash
gh workflow run release-status.yml -R Cringe-Driven-Development-Team/frontend --ref main
```

Для Project API используется организационный `ADD_TO_PROJECT_PAT`, проверяемый
через `viewerCanUpdate` и фактическую запись `Status`; репозиторного токена
для организационной доски недостаточно. При ошибке проверьте доступ PAT,
проект Scrumban №1, поле `Status` и значения `Done`/`Ready for release`.
Отсутствующая карточка даёт ошибку, новая автоматически не создаётся.

### Журнал уведомлений

Непроизводственное окружение Deployments `release-automation` хранит baseline,
ключи `ready:<SHA>` и `queue:<event ID>`, неизменяемый текст, состав PR и ссылку
на отчёт. Оно не участвует в выборе выпуска, rollback или retention.

- `pending` — отправка ещё не начата либо Telegram подтвердил отказ.
- `in_progress` — отправка началась, её исход пока не подтверждён в GitHub.
- `success` — есть подтверждённый `telegram_message_id`; повтор не отправляет.
- `inactive` / `already_deployed` — ожидающее ready-сообщение погашено: выбранный
  SHA уже вошёл в успешную выкатку. Сообщение «ждёт выкатки» больше не нужно.

При timeout или падении runner после отправки сообщение могло дойти, а запись
`success` — нет. `in_progress` автоматически не пересылается. Найдите указанный
в ошибке Deployment и ключ, проверьте тему Telegram. Если сообщение есть,
запишите подтверждение (ID — именно сообщения, а не темы):

```bash
gh api --method POST repos/Cringe-Driven-Development-Team/frontend/deployments/DEPLOYMENT_ID/statuses \
  -f state=success -f description='telegram_message_id=MESSAGE_ID' -F auto_inactive=false
```

Только если достоверно установлено, что сообщение **не отправлено**, верните
запись в `pending` и повторите `Release status`:

```bash
gh api --method POST repos/Cringe-Driven-Development-Team/frontend/deployments/DEPLOYMENT_ID/statuses \
  -f state=pending -f description='Проверено: сообщение не отправлено' -F auto_inactive=false
```

Не сбрасывайте `in_progress` вслепую: GitHub и Telegram не имеют общей транзакции.

### Настройка

Environment `production` (`Settings` → `Environments`, только из `main`, правила одобрения не
меняются):

| Что        | Имя                      | Откуда                                                                   |
| ---------- | ------------------------ | ------------------------------------------------------------------------ |
| секрет     | `S3_ACCESS_KEY`          | `pulumi stack output s3AccessKey --show-secrets` (infra)                 |
| секрет     | `S3_SECRET_KEY`          | `pulumi stack output s3SecretKey --show-secrets` (infra)                 |
| секрет     | `DEPLOY_SSH_KEY`         | приватный ключ CI, его `.pub` — в `ansible/files/authorized_keys/` infra |
| секрет     | `SSH_KNOWN_HOSTS`        | host key `cellestial.ru`, сверенный по fingerprint из консоли            |
| секрет     | `ANSIBLE_VAULT_PASSWORD` | пароль `inventory/group_vars/all/vault.yml` infra                        |
| переменная | `S3_ENDPOINT`            | `pulumi stack output s3Endpoint`                                         |
| переменная | `S3_BUCKET`              | `pulumi stack output s3Bucket`                                           |
| переменная | `CDN_URL`                | `pulumi stack output cdnCustomDomain`                                    |

Environment `release-artifacts` создаётся первой записью сам; секретов в нём нет. GHCR credentials
для выкатки не нужны. `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` — секреты организации.

> [!WARNING]
> Ключ S3 действует на весь проект Selectel, а не только на бакет релизов: ограничение
> environment веткой `main` снимать нельзя
